\section{Overall Architecture}

Figure~\ref{fig:tac-high-level-architecture} shows the final architecture at a high level. The system is separated into access, identity, application, data, privileged administration, and monitoring areas.

This separation was used to keep user traffic, authentication, database access, administration, and monitoring as distinct parts of the design.

The main access path is through the TAC CMS web application. The application sits between users and the SQL Server database, so case and subject records are only reached through the controlled web/API layer.

Authentication and role information are supplied through Active Directory and ADFS, while pfSense and VLANs control which network paths are allowed.

The diagram also separates implemented components from future or supporting components. Wazuh is used for monitoring, while tamper resistant object storage is treated as a future improvement rather than a completed core feature.

\section{Network and VLAN Architecture}

The TAC CMS network was built using a segmented VLAN design instead of placing all systems on one flat subnet. A TP-Link TL-SG108E managed switch was used so that separate services could be placed into different internal networks while still using the same physical switching infrastructure. This allowed production users, servers, management systems, and VPN/admin access to be separated logically.

Trunking was implemented between pfSense, the managed switch, and the Proxmox hosts. The pfSense interface acted as the routing and firewall point for the VLANs, while the TP-Link switch carried tagged VLAN traffic between the firewall and virtualisation hosts. Proxmox then presented the required VLANs to the virtual machines depending on the role of each server. This made it possible to host multiple isolated services on the same physical lab infrastructure without merging them into one broadcast domain.

The internal addressing followed the private IPv4 address ranges defined by RFC 1918. The project used the 10.0.0.0/8 private address space, with each VLAN assigned its own subnet. This ensured that all infrastructure services remained private and were not directly routable on the public Internet.

\section{Identity and Federation Architecture}

The identity architecture was based on two Active Directory domains: TACCENTRAL.COM and TACCORP.COM. 

TACCENTRAL.COM represents the enterprise environment used for managed endpoints and internal services, while TACCORP.COM represents the production identity environment used for higher control access of the CMS. A trust relationship was configured so that identity information could be used across the environment where required.

ADFS was hosted on the TACCENTRAL.COM side of the architecture so this means the application does not need to manage local user passwords. Instead, authentication is handled by the domain identity infrastructure which in this case is the windows server.

\section{Application, API \& Database Architecture}

SQL Server was deployed on a separate domain joined Windows Server on Proxmox under VLAN 31 to separate the application and data layers. Joining the server to TACCORP.COM allowed it to receive organisational management controls such as Group Policy and certificate trust.

For the lab environment, TACCORP Administrator account was used during setup and validation. In production, this would be replaced with a dedicated Active Directory service account for the TAC CMS database connection.

That account would be granted only the required SQL permissions and would be audited separately from administrator accounts.

\section{Application, API \& Database Architecture}

The TAC CMS application was built using Next.js and deployed separately from the SQL Server database. The application layer provides the browser-based interface for the case registry, subject registry, analytics dashboard, audit trail, and bulk import workflow. Database access is handled through backend API routes rather than direct client-side connections.

The API layer acts as the control point between the interface and SQL Server. When a user creates, edits, deletes, restores, imports, or views records, the request is processed by an API route. This allows role checks, validation, SQL interaction, and audit logging to occur before a response is returned to the user.

\section{Monitoring and Audit Architecture}

Monitoring was implemented using Wazuh agents deployed across the main Windows and Linux hosts in the TAC environment. This provided infrastructure visibility for the systems supporting the case management platform, including the domain controllers, SQL Server, web application server, and VPN server.

The monitoring layer is separate from the TAC CMS application audit trail. Wazuh records host-level and security-relevant events from servers, while the TAC CMS audit trail records application-level actions such as case creation, subject creation, soft deletion, restoration, and record access. Together, these provide visibility at both the infrastructure and application layers.
