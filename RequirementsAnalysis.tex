\section{Overview of Requirements Analysis}

The requirements analysis stage defined what the TAC system needed to achieve before detailed design and implementation began. This chapter identifies the business, functional, non-functional, security, identity, infrastructure, data management, audit, and data protection requirements that shaped the final system. The purpose of this stage was to translate the original project idea into a clear set of system expectations that could later be designed, implemented, and validated.

TAC was developed as a secure case management platform rather than a general purpose database or simple web application. This distinction is important because the system needed to support sensitive investigative style records, controlled access, persistent storage, auditability, and secure infrastructure hosting. The requirements therefore covered both the user facing application and the underlying technical environment required to support it.

The requirements were influenced by several practical questions. The first question was what a user should be able to do within the system. This included creating cases, managing subjects, importing records, viewing analytics, and reviewing audit activity. The second question was who should be allowed to perform each action. This introduced the need for role based access control, centralised identity, and security group mapping. The third question was where and how the system should be hosted. This introduced requirements for network segmentation, firewall rules, server isolation, encrypted traffic, and monitoring.

The final set of requirements reflects an enterprise style security model. The system needed to demonstrate that sensitive information could be protected not only by application logic, but also by infrastructure controls. As a result, the requirements analysis stage became the foundation for the high level design, systems architecture, implementation, and validation chapters that follow.

\section{Business Requirements}

The business requirements describe the system from the perspective of an organisation that needs to manage sensitive case information securely. The primary business requirement was to provide a secure web based platform for storing, viewing, and managing investigative case records. The system needed to support the core activities of a case management environment while maintaining control over who could access or modify information.

A key business requirement was that the system should be usable by different operational roles. In a realistic organisation, not every user has the same responsibilities. Some users may need to create or update records, while others may only need to view information or analyse trends. TAC therefore needed to support a role driven model where access to features could be based on job function rather than being identical for all users.

Another business requirement was that the system should support field or remote access in a controlled way. The project was designed around the idea that authorised users may need to access case information from outside a single fixed workstation. However, this access should not weaken security. Remote access therefore needed to be considered alongside VPN access, identity verification, encrypted communication, and network restrictions.

The system also needed to support collaboration and future partner interaction. Although the final implementation focused on the core internal platform, the design considered how partner organisations or external users could eventually interact with the platform through controlled identity and access mechanisms. This requirement influenced the use of federated identity concepts and claims based access.

Bulk import was also an important business requirement. A case management system may need to ingest multiple records from structured files, legacy exports, open-source intelligence exercises, or prepared operational datasets. The ability to import synthetic case and subject data allowed the system to be populated quickly for testing, analytics, and demonstration. This also helped the final project stand out because it allowed the platform to demonstrate behaviour at a larger scale than manual data entry alone.

Finally, the system needed to provide accountability. In a sensitive environment, it is not enough to know that a record exists. The organisation must also be able to identify who created, changed, imported, or deleted information. Auditability was therefore a business requirement as well as a technical requirement.

\section{Functional Requirements}

Functional requirements define the actions that the system must allow users to perform. The first functional requirement was case management. Users with the correct permissions needed to be able to create new case records, view existing cases, update case details, and delete or remove test records where appropriate. Each case record needed to contain structured information such as case reference, title, case type, priority, status, sensitivity level, department, dates, and descriptive notes.

The second functional requirement was subject management. The platform needed to store information about subjects connected to cases. The term subject was chosen instead of person because it better reflects investigative and intelligence led systems where an individual may be a suspect, witness, victim, reporter, missing person, or other relevant entity. Users needed to be able to create, view, update, and delete subject records.

The third functional requirement was the ability to link case and subject information. A case management platform becomes more useful when it can show relationships between records. Although relationship modelling may be extended further in future versions, the final system needed to support the idea that subjects could be associated with cases and that case records were not isolated from the wider subject registry.

The fourth functional requirement was bulk import. The system needed to allow structured test records to be imported into the platform rather than relying only on manual entry. This was important for validating the system with a realistic volume of records and for demonstrating analytics and search behaviour. The bulk import process also required validation so that imported data would follow the expected structure.

The fifth functional requirement was analytics. The system needed to present summary information from the stored data. This included visual or numerical summaries such as total cases, case status distribution, case priority distribution, subject counts, or other useful operational metrics. Analytics helped demonstrate that the database was not only storing records but could also support decision making and oversight.

The sixth functional requirement was audit log visibility. The system needed to provide a way to view recorded actions. Audit logs were required to support accountability by showing activity such as record creation, update, deletion, or import events.

The seventh functional requirement was navigation and usability. The application needed a clear dashboard style layout with separate areas for cases, subjects, analytics, and audit information. The interface needed to be understandable without requiring technical knowledge of the underlying infrastructure.

\section{Non Functional Requirements}

Non functional requirements describe the qualities the system must have rather than individual features. The first non functional requirement was security. TAC needed to protect sensitive records by combining access control, authentication, network restrictions, encrypted communication, and audit logging. Security was treated as a core quality of the system rather than an optional feature.

The second non functional requirement was usability. A secure system is less effective if users cannot operate it correctly. The interface therefore needed to be clear, consistent, and suitable for users who need to manage cases quickly. Pages such as the case registry, subject registry, analytics dashboard, and audit log needed to follow a consistent design so that users could understand the system easily.

The third non functional requirement was maintainability. The project needed to be structured so that features could be modified, extended, and debugged. This influenced the use of reusable components, API routes, SQL backed data access, GitHub version control, and a branch based development workflow.

The fourth non-functional requirement was reliability. The system needed to persist data in a proper database rather than only using browser storage or temporary mock data. This was one of the reasons the project moved from an early prototype data store to Microsoft SQL Server.

The fifth non functional requirement was scalability at a proof of concept level. The system was not required to serve thousands of users in production, but it needed to be designed in a way that could be extended. Separating the web application, database, identity provider, and monitoring components made the architecture more scalable than a single machine prototype.

The sixth non functional requirement was auditability. Important actions should be traceable. This supports internal accountability and future forensic review. Auditability was considered across both the application layer and infrastructure monitoring layer.

The seventh non functional requirement was performance. The system needed to respond appropriately during normal use, including case listing, subject listing, data entry, and bulk import. Although performance benchmarking was not the main focus of the project, the system needed to be efficient enough for demonstration and validation.

\section{Security Requirements}

Security requirements were central to the project. The first security requirement was that users should not be trusted simply because they are connected to the internal network. Access needed to be based on verified identity and assigned permissions. This aligns with the Zero Trust principle of never assuming trust based only on network location.

The second security requirement was least privilege. Users should only receive the access required for their role. A read only user should not be able to create, edit, or delete records. A user responsible for case creation should not automatically receive administrative access. This requirement shaped the role-based access control model.

The third security requirement was network segmentation. Infrastructure components needed to be separated into logical network zones. User devices, servers, management systems, and security services should not all exist on a flat network. VLAN segmentation and pfSense firewall rules were used to reduce unnecessary access between systems.

The fourth security requirement was database isolation. Users should not access SQL Server directly. Instead, users interact with the web application, and the application communicates with the database through controlled API logic. This reduces the exposure of the database server and allows application-level validation and auditing.

The fifth security requirement was encrypted communication. Access to the web application and identity services needed to use SSL/TLS certificates where appropriate. This was required to protect credentials, tokens, and session related traffic in transit.

The sixth security requirement was monitoring. The infrastructure needed a way to observe system behaviour and security relevant events. Wazuh was included to provide monitoring visibility across supported hosts.

The seventh security requirement was controlled administrative access. Administrative actions should be separated from normal user activity and restricted to appropriate management networks or privileged accounts.

\section{Identity and Access Requirements}

Identity and access requirements defined how users would authenticate and how permissions would be applied. The first identity requirement was centralised authentication. TAC was designed to use Active Directory as the identity foundation rather than maintaining separate local user accounts inside the application. This allowed users, groups, and roles to be managed from a central directory.

The second identity requirement was federation. Active Directory Federation Services was selected to provide a claims based authentication model. This allowed identity information from Active Directory to be passed to the web application in a structured way. Claims based identity was important because the application needed to make access decisions based on user attributes or group membership.

The third identity requirement was role-based access control. Users needed to be assigned roles based on Active Directory security groups. Application permissions could then be mapped to roles such as reader, case lead, operations user, or administrator. This approach is more manageable than assigning permissions individually to each user.

The fourth identity requirement was separation of duties. Administrative users, standard users, and read only users should not share the same permission level. This reduces the risk of accidental or intentional misuse.

The fifth identity requirement was future extensibility. The identity model needed to support future improvements such as multi-factor authentication, partner federation, or more granular claims. Although not every future feature was implemented, the final design needed to avoid locking the platform into a weak identity model.

\section{Infrastructure Requirements}

The infrastructure requirements defined the technical environment required to host the system securely. The first infrastructure requirement was virtualisation. The project required a lab environment capable of hosting multiple systems, including domain controllers, SQL Server, web application hosting, firewalling, and monitoring components. Proxmox was used as part of the virtualisation environment.

The second infrastructure requirement was routing and firewall control. pfSense was selected to provide gateway, firewall, and VLAN routing functionality. This allowed the project to implement realistic network segmentation rather than hosting all systems on the same subnet.

The third infrastructure requirement was VLAN separation. The project required separate networks for production users, servers, management, and VPN or administrative access. This separation helped demonstrate that the network design supported the security model.

The fourth infrastructure requirement was Windows Server support. Active Directory, ADFS, and SQL Server required Windows Server infrastructure. This included domain controller configuration, DNS, certificate handling, and SQL Server installation.

The fifth infrastructure requirement was Linux web hosting. The web application was hosted on a Linux server, which communicated with the Windows SQL Server and the ADFS Domain Controller over the internal network. This reflected a realistic mixed platform environment.

The sixth infrastructure requirement was DNS resolution. The system required reliable name resolution between internal services, especially for domain, ADFS, and web application access. DNS was therefore a necessary infrastructure component.

The seventh infrastructure requirement was certificate support. Internal SSL/TLS certificates were required so that services could be accessed over HTTPS. This was especially important for authentication and secure web access within the intranet.

\section{Data Management Requirements}

The data management requirements focused on how case, subject, and audit information should be stored and handled. The first requirement was persistent storage. The system needed to store records in a database so that data remained available after browser sessions or application restarts. This requirement led to the use of Microsoft SQL Server.

The second requirement was structured data. Case and subject records needed consistent fields so that they could be searched, displayed, imported, and analysed. Structured storage also supported future reporting and audit functions.

The third requirement was unique record identification. Case and subject records needed unique identifiers or references. This is important in any case management system because records must be distinguishable and traceable.

The fourth requirement was support for imported data. The system needed to accept structured synthetic data through a bulk import process. This required the data model to be predictable enough for imported records to map correctly into database fields.

The fifth requirement was data integrity. The system needed to reduce the chance of malformed or incomplete records entering the database. Validation at the application and import layer was therefore required.

The sixth requirement was separation between real and synthetic data. For ethical and data protection reasons, the project used synthetic records only. The system was designed and tested without using real personal or investigative data.

The seventh requirement was audit related storage. Actions performed on records needed to be recorded so that user activity could be reviewed. This helped support accountability and validation.

\section{Audit and Monitoring Requirements}

Audit and monitoring requirements were included because the platform handles sensitive style records. The first requirement was application level audit logging. The system needed to capture important user actions such as creating, updating, deleting, or importing records. These events provide a record of activity that can be reviewed later.

The second requirement was infrastructure monitoring. Security events and system activity should not only be visible inside the web application. The underlying servers also needed monitoring so that system behaviour could be observed. Wazuh was selected for this purpose.

The third requirement was accountability. The system should support the ability to identify what action occurred, when it occurred, and which user or system component was involved. This is important in any environment where sensitive records are processed.

The fourth requirement was validation evidence. Monitoring and audit logs were not only included for operational reasons. They also provided evidence that the system was functioning and that testing activity could be demonstrated in the report.

The fifth requirement was future tamper resistance. While the final project focused on core audit logging and monitoring, the design considered how audit logs could be strengthened in future through append only or object lock storage concepts. This requirement supports future work on stronger evidence preservation and forensic reliability.

\section{GDPR and Data Protection Requirements}

Although the project used synthetic data, data protection requirements were still considered because the system is modelled on a case management environment. The first data protection requirement was to avoid real personal data during development and testing. No real victim, suspect, witness, law enforcement, or operational case data was used. This reduced ethical risk and ensured that the project could be tested safely.

The second requirement was data minimisation. The system should only store fields that are useful for case and subject management. In a real deployment, unnecessary personal information would increase risk and would be harder to justify under data protection principles.

The third requirement was access limitation. Only authorised users should be able to access case and subject records. This was addressed through identity based access control and role mapping.

The fourth requirement was accountability. The system should be able to show when records were created or changed and by whom. Audit logging supports this requirement by maintaining a record of user activity.

The fifth requirement was security of processing. The system needed appropriate technical measures to protect data, including HTTPS, network segmentation, database isolation, and monitored infrastructure.

The sixth requirement was retention awareness. Although a full retention engine was not implemented, the system design considered that case data should eventually support retention categories, review dates, or archival policies. This is especially important for a real system handling sensitive data.

The seventh requirement was transparency in the use of AI tools. AI tools were used only as supporting tools during development, such as for UI inspiration and synthetic test data generation. The final system design, implementation decisions, configuration, validation, and report content were reviewed and adapted by the author.

\section{Summary of Requirements}

The requirements analysis established that TAC needed to be more than a basic case database. The system required a secure application layer, persistent database storage, centralised identity, role based access control, network segmentation, encrypted access, monitoring, audit logging, and ethical synthetic test data.

From a business perspective, the platform needed to support secure case and subject management for different user roles. From a functional perspective, it needed to provide CRUD operations, bulk import, analytics, and audit visibility. From a security perspective, it needed to follow least privilege, avoid implicit trust, and protect sensitive-style records through identity and infrastructure controls.

The requirements also influenced the technology choices used later in the project. Active Directory and ADFS were selected to support identity and claims. SQL Server was selected for persistent structured storage. pfSense and VLANs were selected for segmentation and firewall control. Wazuh was selected for monitoring. Next.js was selected for the web application and API layer.

This requirements analysis provided the basis for the high-level design decisions described in the next chapter. Each design choice can be traced back to a requirement identified in this chapter, and each implemented feature is later validated through testing.
