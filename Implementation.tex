\section{Network and Firewall Implementation}

\section{Windows Server, Active Directory \& ADFS Implementation}

The Windows Server identity layer was implemented to provide managed authentication and role assignment for the TAC CMS. Two Active Directory domains were used in the environment: TACCENTRAL.COM and TACCORP.COM. The purpose of this design was to separate the enterprise identity environment from the production-facing identity environment used by the case management platform.

The implementation depended on four main checks: network connectivity, DNS resolution, domain discovery, and ADFS service availability. These were validated from both sides of the environment because federation and role based access depend on reliable communication between the domain controllers.


The first validation step was basic connectivity between the two domain controllers. This confirmed that routing and firewall policy allowed the identity servers to communicate before DNS and trust validation were tested.

ADFS was implemented to provide the federation layer for TAC CMS authentication. The ADFS role and service were checked using PowerShell to confirm that the role was installed and that the federation service was running.

Active Directory security groups were also created to support TAC CMS role-based access. These groups were used to assign users to application roles instead of hardcoding access per user. This made the access model easier to manage and test.

The Windows Server and ADFS implementation provided the identity foundation for the TAC CMS. Connectivity, DNS resolution, domain discovery, ADFS availability, and AD security groups were validated before the application-level RBAC behaviour was tested. This ensured that role-based access in the web application was supported by managed domain identity rather than local application accounts.

\section{SSL Certificate Implementation}

SSL/TLS certificates were implemented so that the TAC CMS web application and ADFS authentication endpoint could be accessed over HTTPS. This was required because authentication traffic, claims, session data, and application activity should not be transmitted over plain HTTP.

\vspace{1cm}

The TAC CMS web application uses the internal hostname portal.taccentral.com. A certificate for this hostname was installed on the Linux web server and referenced inside the Nginx HTTPS configuration. The private key remained on the web server and was not exported or shown in the report.

\vspace{1cm}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.88\textwidth]{Images/nginx_portal_ssl_config.png}

    \vspace{0.8cm}
    
    \caption{Nginx HTTPS configuration showing the certificate and private key paths used for the TAC CMS web application.}
    \label{fig:nginx-portal-ssl-config}
\end{figure}

Figure~\ref{fig:nginx-portal-ssl-config} shows that Nginx was configured to serve portal.taccentral.com over HTTPS using the certificate and private key stored on the web application server. Only the file paths are shown, as the private key itself should never be exposed in documentation.

The client machine was also configured to trust the internal certificate authorities used by the environment. OpenSSL was used to validate both exported root CA certificates and the live HTTPS certificates presented by ADFS and the TAC CMS web application.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{Images/openssl_certificate_validation.png}
    \vspace{1cm}
    \caption{OpenSSL validation of the internal root CA certificates, ADFS certificate, and TAC CMS web application certificate from the client machine.}
    \label{fig:openssl-certificate-validation}
\end{figure}

Figure~\ref{fig:openssl-certificate-validation} confirms that two internal certificate authorities were present in the environment. 

The TACCORP-TAC-DC-CORP-01-CA} certificate was used to issue the TAC CMS web application certificate for portal.taccentral.com. The TACCENTRAL-TAC-DC-ENT-01-CA-1 certificate was used to issue the ADFS certificate for adfs.taccentral.com

The OpenSSL output also confirmed that the live certificates matched the hostnames used by the services. The ADFS certificate contained subject alternative names for adfs.taccentral.com and certauth.adfs.taccentral.com. The TAC CMS certificate contained the subject alternative name portal.taccentral.com. This confirmed that the DNS names, certificate subjects, and HTTPS endpoints were aligned correctly.

The SSL certificate implementation therefore provided encrypted access to both the web application and the ADFS authentication service. It also confirmed that the internal trust chain was working from the client machine, which was required to avoid browser certificate warnings and authentication errors inside the private intranet.

\section{RBAC \& Federated Claims Implementation}

ole-Based Access Control was implemented using Active Directory security groups and ADFS claim rules. The aim was to avoid managing application permissions directly against individual users. Instead, users were organised in Active Directory and assigned to TAC CMS role groups, while ADFS issued the role information to the web application during authentication.

\begin{figure}[H]
\centering
\small

\begin{minipage}[c]{0.38\textwidth}
    \centering
    \includegraphics[width=0.95\linewidth]{Images/ad_tac_ou_structure.png}

\hspace{0.04\textwidth}
\begin{minipage}[c]{0.50\textwidth}
    \raggedright
    \setlength{\baselineskip}{1.25\baselineskip}
    The Active Directory structure was created under the TAC-INDUSTRIES OU in TACCORP.COM. The structure separated users, global role groups, delegated administrators, and service accounts. The TAC-USERS OU was further divided into bureau based units such as TINTEL, TNCCB, TNDOCB, TNECB, TNIB, TINPSB, and TNSU. This allowed users to be organised by operational area while role permissions were handled through separate global security groups.
\end{minipage}

\caption{Active Directory OU structure used to organise TAC Industries users and role groups.}

The main TAC CMS role groups were stored under the global roles structure. These groups represented application permission levels such as read-only intelligence access, operational create access, case lead CRUD access, infrastructure access, and emergency breakglass access.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.86\textwidth]{Images/ad_tac_role_groups.png}
    \caption{Active Directory global security groups created for TAC CMS role-based access control.}
    \label{fig:ad-tac-role-groups}

The role groups shown in Figure~\ref{fig:ad-tac-role-groups} were used as the basis for TAC CMS access decisions. For example, TAC-INTEL-READ represented read-focused access, TAC-OPS-CR represented operational create access, and TAC-LEAD-CRUD represented case lead access with create, read, update, delete, analytics, and audit permissions.

\vspace{0.6cm}

ADFS was configured with a TAC CMS Portal application entry and claim issuance rules. After a user authenticated successfully, ADFS issued the relevant identity and role claims to the web application. The application then used these claims to map the user to the correct TAC CMS role.

\vspace{0.4cm}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{Images/adfs_tac_cms_claim_rules.png}

\end{figure}

Figure~\ref{fig:adfs-tac-cms-claim-rules} shows the TAC CMS Portal configuration and the claim rules created for the application. The LDAP core claims rule issued identity fields such as UPN, name, bureau, and email. Additional rules were created for TAC CMS role groups including TAC-LEAD-CRUD, TAC-INTEL-READ, TAC-OPS-CR, and TAC-ADMIN-BREAKGLASS.

This implementation allowed role assignment to be controlled from Active Directory while ADFS handled the claim issue process. The TAC CMS could then use the received claims to apply the correct access policy after login.
