\section{Technology Selection \& Security}

The technology stack and model implemented was selected to keep the platform realistic, affordable, and reproducible in a lab or small organisation.

Most of the core components used in the project are open source or available at no software licence cost for the project environment. 

This allowed the system to be built as a low cost information system, with the main costs being physical equipment, electricity, ISP connectivity, and the static public IP address used for external/VPN related access.

The aim was not to depend on expensive commercial security platforms. Instead, the project demonstrates how a secure case management environment can be assembled using commonly available infrastructure tools.

pfSense provided firewalling and VLAN control, Proxmox provided virtualisation, Next.js provided the application framework, and Wazuh provided monitoring. 

Microsoft SQL Server and Windows Server were used for the database and identity environment because they are common in enterprise networks and suitable for demonstrating Active Directory, ADFS, and SQL backed application storage.


This approach made the project technically realistic while keeping it achievable. It also reflects how smaller organisations could prototype secure internal systems without immediately relying on high cost commercial platforms.








The security model was influenced by the NIST SP 800-207 Zero Trust Architecture model. In TAC CMS, users are not trusted simply because they are connected to the internal network. Access decisions are based on Active Directory identity, ADFS claims, group membership, application role mapping, and network controls.

\section{Access Control \& Data Protection}


Access control was implemented around a role based model. In this design, users are not given permissions individually inside the application. Instead, access is linked to Active Directory group membership, ADFS claims, and the role assigned to the user inside the TAC CMS.

This follows the principle that access control should define who can access a resource, under what conditions access is allowed, and what actions the user can perform. In the TAC CMS, the protected resources are case records, subject records, audit logs, analytics, and administrative actions.

The role model also made the system easier to validate. A user with no valid domain account cannot authenticate. A valid domain user without the correct TAC security group receives limited access. A correctly assigned user receives the expected role claim and can access the relevant application features. This allowed access control to be tested directly through the GUI by comparing the options shown to different users.

Data protection was considered even though the project used synthetic data only. No real case records, victim data, suspect data, witness data, private investigation records, social care records, or operational law enforcement data were used during testing. This allowed the system to demonstrate realistic workflows without processing real personal data.

All testing and bulk import records were fictional and created for demonstration purposes only. ChatGPT was used to assist with generating sample test records, but the generated data was not based on real people, real investigations, or real operational datasets.

The data model was kept limited to the fields required for case management, subject management, auditing, and analytics. This supported data minimisation by avoiding unnecessary fields that would increase privacy risk in a real deployment.

In a real production deployment, further data protection work would be required. This would include a formal DPIA, data retention policy, backup policy, incident response plan, MFA, and documented data governance procedures.
